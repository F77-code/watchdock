# Watchdock

Сайдкар для Docker Compose. Он следит за логами и событиями одного проекта, в момент сбоя снимает состояние хоста и соседних контейнеров, просит языковую модель собрать короткий разбор и отправляет карточку в Telegram.

Это не платформа наблюдаемости. Нет базы, агента в каждом сервисе и архива логов. Есть один процесс с потолком 0.5 CPU и 256 МБ.

## Возможности

- Читает логи и события контейнеров одного Compose-проекта: `die`, `oom`, `restart`, `start`, `health_status`.
- На падении собирает хвост логов, load average, память, свободное место и статусы соседей.
- Просит OpenAI-совместимую модель вернуть разбор по фиксированной схеме. Если модель недоступна или ответила не по схеме, в чат всё равно уходит аварийная карточка.
- Шлёт HTML-карточку в Telegram. Повтор той же ошибки глушится только после успешной доставки.
- Держит жёсткий потолок: 0.5 CPU, 256 МБ, не больше двух разборов сразу, ограниченный хвост логов и ограниченная карта сигнатур.

## Когда Watchdock не подходит

Не ставьте его вместо системы, которой нужны:

- поиск по логам за недели, графики и SLO;
- трейсы и разбор одного пользовательского запроса;
- расписание дежурств, подтверждение алёрта и эскалация;
- Kubernetes или несколько хостов;
- автоматический рестарт или откат без человека.

Команды в карточке пишет модель. Их нужно прочитать. Сайдкар ничего не исполняет и ничего не чинит.

## Требования

- Docker Compose на одном хосте
- Python 3.12, если запускаете процесс без образа
- Ключ OpenAI-совместимого API (`OPENAI_API_KEY`, при необходимости свой `OPENAI_BASE_URL`)
- Бот Telegram и id чата

## Установка

Из корня репозитория:

```bash
cp .env.example .env
```

Заполните в `.env` три значения: `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Пустое значение процесс не примет и завершится до подключения к Docker.

```bash
docker compose up -d --build
```

Поднимутся два сервиса. `docker-proxy` — read-only proxy к сокету демона. `watchdock` ходит только в него по `tcp://docker-proxy:2375` и сокет демона не монтирует.

Лимит `deploy.resources` Compose применяет в Swarm. Для обычного `docker compose up` рядом заданы `cpus` и `mem_limit`.

## Быстрый старт

`COMPOSE_PROJECT_NAME` можно не задавать. Тогда сайдкар читает лейбл `com.docker.compose.project` со своего контейнера и следит за этим проектом. Чужие проекты на том же демоне игнорируются. Контейнер `watchdock` и имена из `IGNORED_CONTAINERS` тоже.

Проверка, что процесс жив:

```bash
docker compose logs -f watchdock
```

Раз в `HEARTBEAT_SEC` (по умолчанию 300 секунд) в логе появляется `sentinel is alive` с числом живых подписок на логи и числом неудачных отправок. Тот же тик обновляет `/tmp/watchdock-heartbeat`. HEALTHCHECK считает контейнер живым, если файл моложе двух интервалов heartbeat. Первые 600 секунд после старта Docker ещё не решает по этому файлу.

## Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | пусто | Пусто — проект этого Compose. Иначе имя другого проекта на том же демоне |
| `OPENAI_API_KEY` | нет | Ключ OpenAI-совместимого API. Пустое значение отвергается |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | Прокси или локальная модель |
| `OPENAI_MODEL` | `gpt-5-nano` | Имя модели |
| `TELEGRAM_BOT_TOKEN` | нет | Токен бота. Пустое значение отвергается |
| `TELEGRAM_CHAT_ID` | нет | Чат или канал. Пустое значение отвергается |
| `LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` или `CRITICAL` |
| `BUFFER_SIZE_LINES` | `200` | Сколько последних строк держать на контейнер. Сверху ограничено |
| `DEBOUNCE_WINDOW_SEC` | `5` | Сколько ждать соседние строки после первого срабатывания |
| `COOLDOWN_PERIOD_SEC` | `300` | Пауза по той же сигнатуре после успешной отправки. Этот срок пишется в карточку |
| `MIN_SEVERITY` | `LOW` | Ниже этого уровня карточка не уходит: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `IGNORED_CONTAINERS` | пусто | Дополнительные имена через запятую |
| `HOST_DISK_PATH` | `/` | Путь, у которого спрашивать свободное место |
| `HEARTBEAT_SEC` | `300` | Период строки heartbeat и файла для HEALTHCHECK |
| `HEARTBEAT_PATH` | `/tmp/watchdock-heartbeat` | Файл, по которому Docker видит живой цикл |
| `DOCKER_HOST` | в Compose `tcp://docker-proxy:2375` | Куда подключаться. В коде по умолчанию unix-сокет, Compose его подменяет |

Пример без секретов лежит в [`.env.example`](.env.example).

Внутренние пределы в Compose не вынесены: строка не длиннее 2048 символов, буфер контейнера не больше 500 КБ, таймаут модели 10 секунд, в промпт не больше 80 строк и 24 000 символов. Crash loop — больше 3 рестартов за 120 секунд, затем тишина 15 минут. Telegram пробует отправку 3 раза.

## Как это работает

1. На каждый контейнер проекта открывается `logs` с `follow` и `tail=0`. В разбор попадают только новые строки. Рестарт и новый id отменяют старый поток и открывают новый. Оборванный поток поднимается снова, пока контейнер есть в списке проекта.
2. Строка или событие проходит детектор. Сигнатура — это SHA-256 от имени контейнера и текста, из которого убраны UUID, IP, метки времени и длинные hex-id.
3. Первое срабатывание ждёт `DEBOUNCE_WINDOW_SEC`, чтобы в отчёт попали хвост стека и ошибки соседей.
4. Затем снимаются `/host/proc`, диск и статусы контейнеров. Один неудачный `inspect` не стирает остальных. Одновременно идут не больше двух разборов, чтение логов этим лимитом не блокируется.
5. Модель получает уже очищенный срез. Любая ошибка модели, кроме отмены задачи при остановке, превращается в аварийную карточку с коротким замаскированным фрагментом лога.
6. Если серьёзность ниже `MIN_SEVERITY`, карточка не отправляется: решение уже принято, кулдаун начинается. OOM, почти полная память хоста и сосед в `unhealthy` или `restarting` не опускают серьёзность ниже HIGH.
7. Карточка уходит в Telegram. Сбой сети повторяется до трёх раз. На 429 пауза берётся из `Retry-After`, но все паузы вместе не длиннее 8 секунд. Сообщение длиннее 4096 символов режется целыми блоками, не посреди HTML-тега.
8. Кулдаун ставится только после успешной отправки. Пока отправка падает, та же сигнатура пробует уйти снова не чаще одного раза за окно debounce. После успеха срок в тексте карточки равен `COOLDOWN_PERIOD_SEC`.

`oom` и сразу следующий `die` с кодом 137 по одному контейнеру дают одну карточку. `die` с кодом 0 инцидентом не считается. Серия рестартов схлопывается в один `STUCK_IN_RESTART_LOOP`.

`SIGINT` и `SIGTERM` перестают принимать новые события, досылают уже открытый debounce и только потом закрывают клиентов. Бюджет остановки около 5 секунд. Отмена до успешной отправки кулдаун не включает.

Инцидентом считается строка с маркером `FATAL`, `CRITICAL`, `PANIC`, `Traceback (most recent call last):`, `NullPointerException`, `Segmentation fault`, `SIGSEGV`, HTTP 5xx в access-логе, `connection refused`, `deadlock detected` или `out of memory`. Из событий Docker — `oom`, `die` с ненулевым кодом и `health_status: unhealthy`.

## Безопасность

- Сокет демона смонтирован только в `docker-proxy` и только на чтение. Proxy пропускает GET к контейнерам, событиям, `/version` и `/_ping`. `POST` выключен. Флаг `:ro` сам по себе методы записи не запрещает, их запрещает proxy.
- У `watchdock` сокета демона нет. `/proc` и `/sys` хоста смонтированы в него только на чтение. Стоят `no-new-privileges:true` и `cap_drop: ALL`.
- Процесс остаётся root, чтобы читать cgroup чужих контейнеров в `/host/proc`.
- До буфера и ещё раз перед моделью маскируются bearer, JWT с словом Bearer и без него, пароль в URI, пары `password` / `token` / `secret` / `api_key` с кавычками и без, ключи `sk-` и `AKIA`, PEM. Маска не находит каждый секрет: другая форма может дойти до модели и до чата.
- Над командами в карточке есть пометка, что это непроверенный текст модели.
- Если логи нельзя отправлять наружу, укажите в `OPENAI_BASE_URL` модель в своей сети.
- Фильтр «только наш Compose» стоит в приложении. Не ставьте сайдкар на хост, где в соседних проектах лежат чужие секреты, если этому процессу не доверяете.

## Если что-то пошло не так

**Нет новых строк.** Proxy или демон недоступны. В логе растёт пауза переподключения от 1 до 30 секунд. После сессии длиннее 30 секунд пауза снова начинается с одной. Список контейнеров и подписки собираются заново.

**Модель молчит или ответила не по схеме.** В чат уходит аварийная карточка, если Telegram её принял. Кулдаун после этого есть. Если не принял, следующая такая же ошибка снова дойдёт до отправки после debounce.

**Telegram ответил 429.** Пауза читает `Retry-After` и не копится дольше 8 секунд. Недоставленная карточка кулдаун не включает.

**Сам Watchdock перезапустился.** Кулдауны и хвост логов жили только в памяти, после рестарта они пустые. Старые строки заново не читаются: подписка идёт с `tail=0`. Новая ошибка снова станет карточкой.

**В карточке 0 GB свободно, а на хосте место есть.** Считается `HOST_DISK_PATH`. По умолчанию это корень контейнера, не диск хоста. Примонтируйте нужный путь и укажите его.

**Контейнер `Up`, а лог замер.** HEALTHCHECK смотрит mtime `/tmp/watchdock-heartbeat`. Если файл старше двух `HEARTBEAT_SEC`, Docker перезапустит контейнер.

**Процесс сразу завершился.** Пустой ключ, пустой токен, пустой chat id, неизвестный `MIN_SEVERITY` или неизвестный `LOG_LEVEL`. До proxy выполнение не доходит.

## Разработка

Тесты не требуют демона Docker.

Нужен [uv](https://docs.astral.sh/uv/) 0.9.28: им же собран образ и прогон в GitHub Actions.

```bash
cd watchdock
uv sync
uv run pytest
uv run ruff check config.py main.py core schemas
uv run mypy config.py main.py core schemas
```

Образ ставит зависимости из [`watchdock/uv.lock`](watchdock/uv.lock), не с плавающих нижних границ. В GitHub Actions тот же набор: ruff, mypy, pytest и `docker build`.
