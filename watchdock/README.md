# Watchdock

Watchdock — сайдкар для уже работающего Docker Compose. Он смотрит логи и события контейнеров одного проекта, в момент сбоя снимает состояние хоста и соседей и просит языковую модель собрать короткий разбор. Готовая карточка уходит в Telegram.

Это не платформа наблюдаемости и не дежурная служба. Watchdock закрывает узкий зазор: контейнер упал или написал фатальную строку, а человек должен за минуту понять, что сломалось, кого это задело и какую команду выполнить первой. Для этого не поднимается отдельная база, агент на каждом сервисе и хранилище логов.

Каталог с кодом, сервис в Compose и контейнер называются `watchdock`.

Процесс рассчитан на Python 3.12. В Compose у него жёсткий потолок: 0.5 CPU и 256 МБ памяти. Корень файловой системы контейнера только для чтения, временные файлы живут в `tmpfs` на `/tmp`.

## Для кого

Watchdock уместен, если:

- приложение уже живёт в Docker Compose на одном хосте;
- дежурный читает алерты в Telegram, а не в отдельной консоли;
- полный контур Grafana, Loki и Prometheus ещё не окупается или его некому сопровождать;
- нужен разбор конкретного падения, а не график за месяц;
- модель можно взять любую OpenAI-совместимую, в том числе локальную через `OPENAI_BASE_URL`.

Он плохо подходит, если нужны поиск по всем логам за недели, трейсинг запросов, SLO, расписание дежурств, подтверждение алёрта и эскалация. Это работа других систем. Watchdock можно поставить рядом с ними, но он их не заменяет.

## Чем Watchdock не является

- Не хранилище логов. В памяти только хвост, после рестарта сайдкара он пропадает.
- Не сборщик метрик. Нет графиков, нет истории CPU по минутам, нет записи каждой точки.
- Не APM. Он не видит трейсы, SQL изнутри приложения и путь конкретного запроса, если этого нет в логе.
- Не авторемонт. Команды в отчёте нужно выполнить самому. Сайдкар ничего не рестартит и не правит конфиги.
- Не мультихостовый кластер. Он читает сокет того Docker, к которому подключён.
- Не дежурная платформа. Нет расписания, эскалации, статуса «принято в работу» и постмортема.

## Как устроен один инцидент

1. При старте Watchdock берёт все контейнеры своего Compose-проекта. Если `COMPOSE_PROJECT_NAME` пуст, имя читается с лейбла `com.docker.compose.project` у собственного контейнера. Чужие проекты на том же демоне игнорируются. Сам контейнер `watchdock` и имена из `IGNORED_CONTAINERS` тоже. У каждого принятого контейнера открываются логи, а в момент инцидента снимается его состояние.
2. На каждый подходящий контейнер открывается поток `logs` с `follow` и `tail=0`: в разбор попадают новые строки, а не вся прошлая жизнь контейнера. Рестарт и новый id контейнера отменяют старый поток и открывают новый. Если поток оборвался сам, подписка повторяется, пока контейнер ещё в списке проекта.
3. Параллельно читается поток событий Docker: `die`, `oom`, `restart`, `start`, `health_status`.
4. Строка или событие проходит детектор. Если это инцидент, из текста убираются UUID, IP, временные метки и длинные hex-id. От имени контейнера и очищенного текста считается SHA-256.
5. Первое срабатывание сигнатуры ждёт `DEBOUNCE_WINDOW_SEC` (по умолчанию 5 секунд), чтобы в отчёт попали хвост стека и ошибки соседних сервисов.
6. Когда окно закрылось, Watchdock читает `/host/proc` (load average и память), свободное место на диске и статусы контейнеров проекта: `inspect`, память упавшего через Docker stats, при неудаче — cgroup на `/host/sys`. Один неудачный `inspect` не стирает статусы остальных. Одновременно идут не больше двух таких разборов, чтение логов этим лимитом не блокируется.
7. Секреты вычищаются второй раз, и срез уходит в модель. Ответ обязан совпасть со схемой: суть, серьёзность, класс, причина, радиус поражения, шаги и команды. Любая ошибка модели, кроме отмены задачи при остановке, превращается в аварийную карточку, а не в потерянный инцидент.
8. Если серьёзность ниже `MIN_SEVERITY`, сообщение не отправляется, и кулдаун всё равно начинается: решение уже принято. Если хост почти без памяти, событие — OOM, или сосед в `unhealthy` / `restarting`, серьёзность не опускается ниже HIGH, даже когда модель ответила спокойно.
9. Карточка уходит в Telegram Bot API (`sendMessage`, `parse_mode=HTML`). Сбой сети повторяется до трёх раз. На ответ 429 пауза берётся из `Retry-After`, но все паузы вместе не длиннее 8 секунд. Обрыв связи с демоном не роняет процесс: пауза 1, 2, 4 секунды и далее до 30.
10. Кулдаун на `COOLDOWN_PERIOD_SEC` (по умолчанию 5 минут) ставится только после успешной отправки. Пока отправка падает, та же сигнатура снова пробует уйти не чаще одного раза за окно debounce, а не молчит пять минут. После успеха повтор только увеличивает счётчик. Следующая карточка говорит, сколько раз это случилось, и срок в тексте берётся из `COOLDOWN_PERIOD_SEC`, а не зашит как «5 мин».

`oom` и сразу следом `die` с кодом 137 по одному контейнеру дают одну карточку, а не две.

Пока событий нет, раз в `HEARTBEAT_SEC` (по умолчанию 300 секунд) в лог пишется строка `sentinel is alive` с числом живых follow и числом неудачных отправок. Та же секунда обновляет mtime файла `/tmp/watchdock-heartbeat`. Docker HEALTHCHECK считает контейнер живым, только если этот файл моложе двух интервалов heartbeat. Стартовая пауза проверки — 600 секунд, чтобы первый heartbeat успел случиться.

Остановка по `SIGINT` и `SIGTERM` перестаёт принимать новые события, досылает уже открытый debounce и только потом закрывает клиентов модели и Telegram. Общий бюджет остановки — около 5 секунд. Отмена до успешной отправки кулдаун не ставит и не оставляет сигнатуру в вечном ожидании.

## Что считается инцидентом

Строка лога, если в ней есть один из маркеров:

- `FATAL`, `CRITICAL`, `PANIC`;
- `Traceback (most recent call last):`;
- `NullPointerException`, `Segmentation fault`, `SIGSEGV`;
- HTTP 5xx в access-логе (`HTTP/1.1" 500`);
- `connection refused`, `deadlock detected`, `out of memory`.

События Docker:

- `oom` — даже если в буфере нет ни одной строки. Парный `die 137` в ближайшие секунды отдельно не отправляется;
- `die` с ненулевым кодом выхода, когда это не пара к только что виденному OOM;
- `health_status: unhealthy`.

`die` с кодом 0 инцидентом не считается: это штатная остановка. Событие `restart` само по себе карточку не шлёт. Если один контейнер перезапустился больше трёх раз за 120 секунд, уходит один сигнал `STUCK_IN_RESTART_LOOP`, и следующие 15 минут этот цикл молчит. Иначе контейнер в crash loop засыпал бы чат каждые несколько секунд.

## Как режется шум и память

На контейнер хранятся последние `BUFFER_SIZE_LINES` строк (по умолчанию 200). Строка длиннее 2048 символов обрезается с пометкой `[TRUNCATED]`. На контейнер не больше 500 КБ. Это предел против гигантского Java- или Python-трейса, а не настройка в Compose.

В промпт модели уходит не весь буфер, а хвост: последние 80 строк и не больше 24 000 символов. В контекст инцидента хвост буфера остаётся целиком, насколько хватает лимита.

Секреты маскируются до записи в буфер и ещё раз перед запросом к модели:

- `Bearer` и JWT, в том числе JWT без слова Bearer;
- пароль в URI базы → `[MASKED_PASSWORD]`;
- `api_key`, `secret`, `password`, `passwd`, `token` и без кавычек (`password=secret`) → `[REDACTED]`;
- ключ вида `sk-...` и идентификатор `AKIA...`;
- PEM-блок private key → `[REDACTED_RSA_KEY]`.

Маска не обещает найти каждый секрет. Незнакомая форма в логе может дойти до модели и до чата.

Число разных сигнатур ограничено. Вытесняются только те, у которых кулдаун уже кончился. Буфер контейнера, которого больше нет в проекте, удаляется при следующем списке контейнеров.

Если модель не ответила, вернула пустой ответ или ответ не по схеме, в Telegram уходит аварийная карточка. В причине — короткий уже замаскированный фрагмент последней строки, не сырой хвост целиком, и команда `docker logs --tail 100 <контейнер>`.

Сообщение длиннее 4096 символов режется целыми блоками: сначала соседи, потом команды, потом шаги, затем причина по границе символа. Готовый HTML посреди тега не разрезается. Текст из логов и из модели экранируется. Над командами стоит пометка, что это непроверенный текст модели и его не запускают вслепую.

## Что оказывается в карточке

Уровень задаёт значок: LOW 🟡, MEDIUM 🟠, HIGH 🔴, CRITICAL 🚨.

В сообщении есть время в UTC, имя контейнера, тип триггера (`LOG_ERROR`, `OOM`, `CRASH_EXIT`, `UNHEALTHY`, `STUCK_IN_RESTART_LOOP`), класс сбоя, серьёзность и число повторов. Дальше — влияние, первопричина, срез хоста (load average, процент RAM, свободное место), память и рестарты упавшего контейнера, статусы соседей, шаги и команды. Внизу — id инцидента, чтобы сопоставить карточку с логом сайдкара.

Классы, которые модель обязана выбрать: инфраструктурный OOM, связь с базой, таймаут внешнего API, баг приложения, ошибка конфигурации, нехватка ресурса или неизвестно.

## Плюсы

- Один контейнер. Не нужны Postgres под алерты, Elasticsearch, Prometheus и отдельный воркер.
- Жёсткий потолок 0.5 CPU и 256 МБ. Сайдкар не должен стать причиной OOM на хосте, за которым он следит.
- Смотрит ровно один Compose-проект. Соседний стенд на том же Docker не попадает в чат.
- Ловит OOM и выход 137, когда приложение не успело ничего написать. Детектор по логам в этот момент слеп.
- В одном срезе видны и упавший сервис, и соседи. Если backend умер, а postgres в `unhealthy`, это попадает в промпт, а не остаётся догадкой.
- Шум схлопывается до отправки: debounce, кулдаун после успешной доставки и отдельный режим crash loop. Пока карточка не ушла, повтор не прячется на весь кулдаун.
- Секреты известных форм вырезаются до буфера и второй раз перед моделью. Это не поиск любого секрета.
- Любой OpenAI-совместимый endpoint. Это может быть OpenAI, прокси или локальная модель. От Telegram и от Docker код модели не зависит.
- Если модель лежит или ответила не по схеме, карточка всё равно уходит. В ней короткий замаскированный фрагмент и команда посмотреть логи.
- Отчёт на языке дежурного: что сломалось, кого задело, что сделать. Команды помечены как текст модели. Не ссылка «посмотрите дашборд».
- К демону ходит отдельный proxy, и только на чтение контейнеров, логов, событий, inspect и stats. У сервиса `watchdock` сокета демона нет. Стоят `no-new-privileges` и `cap_drop: ALL`.
- Пока всё тихо, heartbeat пишет в лог живые follow и число неудачных отправок. Docker перезапускает контейнер, если этот файл перестал обновляться.

## Минусы

- Память только до рестарта. Искать «что писалось вчера в 03:14» здесь нельзя.
- Правила логов — регулярные выражения. Необычная ошибка без этих слов не станет инцидентом, пока контейнер не умрёт или не станет unhealthy.
- Модель ошибается. Команда в карточке может быть неверной. Её нужно читать, а не выполнять вслепую.
- Текст логов уходит наружу, если `OPENAI_BASE_URL` указывает на чужой API. Маскирование закрывает известные формы секретов, а не любой ключ в произвольном формате.
- Proxy режет методы записи, но чтение Docker API по-прежнему широкое: список, логи, inspect и stats контейнеров, которые демон отдаёт этому сокету. Фильтр «только наш Compose» стоит в приложении. Не ставьте сайдкар на хост с чужими секретами в соседних проектах, если этому процессу не доверяете.
- Свободное место по умолчанию считается у корня контейнера, а не у диска хоста. Чтобы видеть хост, нужен свой mount и `HOST_DISK_PATH`.
- Один хост и один проект. Swarm, несколько нод и Kubernetes этот сайдкар не покрывает.
- Нет интерфейса, поиска, графиков, подтверждения алёрта и эскалации. Есть Telegram и лог самого Watchdock.
- Нет автодействий. Unhealthy-контейнер сам не перезапустится.
- Карточка режется лимитом Telegram в 4096 символов. Длинная причина сокращается.
- Качество разбора зависит от модели. Маленькая локальная модель даст более слабый текст, чем большая, и это нормальная плата за то, чтобы логи не уезжали.
- Серьёзность от модели можно занизить порогом `MIN_SEVERITY`, но завысить её до CRITICAL автоматика сама не будет: потолок автоподнятия — HIGH.
- История инцидентов не копится. Повтор через сутки выглядит как новый случай, если кулдаун уже прошёл.

## Сравнение с тем, что уже есть

Ниже не рейтинг «кто лучший», а разница задач. Watchdock выигрывает там, где нужен один дешёвый контур «событие Docker → карточка в Telegram» без платформы. Он проигрывает там, где нужна история, графики или процесс дежурства.

### Grafana, Loki, Prometheus, Alertmanager

Это нормальный контур наблюдаемости: метрики, запросы по логам, дашборды, правила и маршруты алертов. Он помнит недели данных и отвечает на вопрос «как это вело себя раньше».

Watchdock этого не умеет. Его преимущество в другом. Стек Grafana надо поставить, хранить и писать правила. Watchdock добавляется одним сервисом в уже существующий `docker-compose.yml` и на падении сам прикладывает хвост логов, соседей и черновик команд. Alertmanager пришлёт факт срабатывания правила. Watchdock пришлёт попытку объяснить этот факт. Для команды из нескольких человек, у которой нет отдельного человека на Grafana, это меньший порог.

Имеет смысл держать оба: Grafana для истории и SLO, Watchdock для ночного падения контейнера.

### Datadog, New Relic, Dynatrace

У них агенты, APM, инфраструктура, логи, аномалии и готовые интеграции. Datadog Watchdog и аналоги ищут отклонения по своим данным. Это сильнее любого сайдкара, если за это платят и согласны отправлять телеметрию в их облако.

Watchdock не строит профиль сервиса и не видит трейсы. Он дешевле по числу компонентов и не требует их агента в каждом контейнере: читает сокет и логи снаружи. Модель и Telegram выбираете вы. Для одного Compose-проекта на VPS счёт Datadog часто больше, чем польза от полного APM. Для продакшена с десятками сервисов и следами запросов картина обратная: Watchdock там только дополнение.

### Sentry и другие error-tracker'ы

Sentry силён, когда в коде стоит SDK: группировка исключений, релизы, пользователь, кадры стека, регрессии. Он почти ничего не знает про OOM killer, `healthcheck` Docker и load average хоста, пока вы сами это туда не положите.

Watchdock не заменяет SDK. Он видит процесс снаружи: контейнер умер, health стал красным, в access-логе пошли 500, postgres рядом перезапускается. Внутренний стек он увидит, только если приложение само написало его в stdout. Для бага в конкретном запросе нужен Sentry. Для «контейнер убит, на хосте кончилась память» нужен Watchdock или метрики.

### Elastic, OpenSearch и серый импорт логов

Поиск по логам за месяцы, дашборды, алерты по запросу. Цена — кластер, индексы, место на диске и человек, который это чинит.

Watchdock не индексирует ничего. Он держит последние 200 строк на контейнер и выбрасывает их в момент инцидента. Если вопрос «найди все 500 за вторник», это Elasticsearch или Loki. Если вопрос «почему этот контейнер только что умер», Watchdock отвечает быстрее и без кластера.

### Netdata

Netdata отлично показывает машину в реальном времени и умеет тревоги по метрикам, включая свои модели аномалий. Это про CPU, диск, сеть и процессы.

Watchdock почти не про ряды метрик. У него один срез в момент сбоя: load average, RAM, диск, память контейнера, статусы соседей. Зато он читает текст лога и события `die` / `oom` и просит модель связать это с соседом. Netdata не заменяет разбор стектрейса. Watchdock не заменяет экран «что с диском последние сутки».

### Dozzle и другие живые просмотрщики логов

Dozzle удобно открыть и смотреть stdout контейнеров. Алертов, дедупликации и разбора там нет. Это окно, а не дежурный.

Watchdock молчит, пока детектор не сработал, и тогда сам пишет в Telegram. Смотреть поток глазами он не предлагает: интерфейса нет.

### Uptime Kuma, Healthchecks.io и прочие проверки «жив ли URL»

Они отвечают на вопрос, открывается ли сайт или пришёл ли heartbeat крона. Они не читают Docker и не отличают OOM от бага в SQL.

Watchdock не пингует URL снаружи. Контейнер может быть `Up`, а пользователи уже получать 500: это как раз лог и healthcheck. Внешнюю проверку доступности Watchdock не выполняет. Её имеет смысл оставить отдельной.

### Autoheal и политики `restart`

`restart: unless-stopped` и autoheal поднимают контейнер снова. Они не объясняют, почему он лёг. На crash loop получается бесконечный рестарт без текста.

Watchdock как раз про этот текст. При серии рестартов он схлопывает их в один `STUCK_IN_RESTART_LOOP`, а не шлёт карточку на каждый `die`. Поднимать контейнер он не будет: это по-прежнему политика Docker или autoheal.

### Komodor, Robusta, K8sGPT, HolmesGPT

Это разбор инцидентов и диагностика для Kubernetes: объекты кластера, поды, события API, иногда автоматические действия. На Compose их не к чему прикрепить.

Watchdock знает лейблы Compose, сокет одного демона и обычные `docker logs`. На кластере Kubernetes он не конкурент этим системам. На одной VM с `docker compose` они избыточны, а он как раз про этот размер.

### PagerDuty, incident.io, Rootly, Grafana OnCall

Они ведут инцидент как процесс: кто дежурит, кто подтвердил, куда эскалировать, какой канал, какой постмортем. Источник алёрта для них может быть любым.

Watchdock — источник, не процесс. Он умеет дойти до Telegram и на этом заканчивается. Если дежурств несколько и нужно «принято / решено», карточку Watchdock можно считать входом, но сам он статусы не хранит.

### Better Stack, Sematext, Axiom, Logtail

Облачные логи и алерты. Быстро подключить, нечего администрировать, данные у провайдера, оплата по объёму.

Watchdock не забирает весь поток логов в чужое хранилище. Наружу уходит урезанный и почищенный срез в момент сбоя, и только в ту модель, чей URL вы указали. Это меньше данных и меньше счёта за гигабайты, и одновременно нет поиска по архиву. Для архива нужен их сервис или свой Loki. Для редкого ночного падения часто хватает среза.

## Когда Watchdock уместнее аналога

Берите Watchdock, если одновременно верно вот что:

- один хост и один Compose-проект;
- дежурный сидит в Telegram;
- нужен разбор падения, а не архив;
- ставить и кормить платформу наблюдаемости сейчас дороже, чем один контейнер с лимитом 256 МБ;
- устраивает, что модель может ошибиться, а человек проверит команду перед запуском.

Берите платформу, а Watchdock не ставьте вместо неё, если нужно любое из этого:

- логи и метрики за недели;
- трейсы и разбор одного пользовательского запроса;
- несколько команд, расписание и эскалация;
- Kubernetes;
- автоматический рестарт или откат без человека.

Самый здравый вариант для уже большого продакшена: Watchdock рядом с существующим стеком, а не вместо него. Платформа хранит историю. Watchdock будит чат, когда контейнер умер.

## Безопасность

- Сокет демона смонтирован только в сервис `docker-proxy`, с `:ro`. Proxy (`tecnativa/docker-socket-proxy:0.4.2`) пропускает GET к контейнерам, событиям, `/version` и `/_ping`. `POST` выключен. Флаг `:ro` на сокете сам по себе методы записи не запрещает — их запрещает proxy.
- Сервис `watchdock` ходит в `tcp://docker-proxy:2375` и сокет демона не монтирует. `/proc` и `/sys` хоста смонтированы в него только на чтение.
- У обоих сервисов стоят `no-new-privileges:true` и `cap_drop: ALL`.
- Процесс Watchdock остаётся root, чтобы читать cgroup чужих контейнеров в `/host/proc`. Сокет для этого больше не нужен.
- Маскирование не обещает найти каждый секрет. Оно закрывает bearer, JWT с Bearer и без него, пароль в URI, пары `password`/`token`/`secret`/`api_key` с кавычками и без, ключи `sk-` и `AKIA`, PEM. Другая форма может пройти.
- Для логов, которые нельзя отправлять наружу, `OPENAI_BASE_URL` должен указывать на модель в вашей сети.

## Запуск

Сервис описан в корневом `docker-compose.yml`. Секреты передаются в окружение того Compose, который его поднимает. Пример имён без значений — в `.env.example`.

`COMPOSE_PROJECT_NAME` можно не задавать. Тогда Watchdock смотрит контейнеры того Compose, в котором запущен сам: логи каждого соседа и их состояние в снимке инцидента. Имя проекта он берёт со своего лейбла. Переменную задают только чтобы следить за другим проектом на том же демоне. Сервисы, которые нужно видеть, должны быть в одном файле с сайдкаром либо в том проекте, чьё имя указано.

```bash
docker compose build watchdock
docker compose up -d docker-proxy watchdock
```

Лимит `deploy.resources` Compose применяет в Swarm. Рядом стоят `cpus` и `mem_limit`: их подхватывает обычный `docker compose up`.

`/proc` → `/host/proc` и `/sys` → `/host/sys` смонтированы в `watchdock` только на чтение. Свободное место на диске по умолчанию считается через `statvfs` корня контейнера. Чтобы видеть диск хоста, примонтируйте его отдельно и укажите `HOST_DISK_PATH`. Ноль гигабайт в карточке чаще значит, что смотрим не тот путь, а не то, что диск хоста пуст.

Обязательны три непустые переменные: `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Пустое значение, неизвестный `MIN_SEVERITY` и неизвестный `LOG_LEVEL` завершают процесс сразу, до подключения к proxy. `MIN_SEVERITY` — это `LOW`, `MEDIUM`, `HIGH` или `CRITICAL`.

## Переменные окружения

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | пусто | Пусто — проект этого Compose. Иначе лейбл чужого проекта на том же демоне |
| `OPENAI_API_KEY` | нет | Ключ к OpenAI-совместимому API |
| `OPENAI_BASE_URL` | `https://api.openai.com/v1` | Чужой прокси или локальная модель |
| `OPENAI_MODEL` | `gpt-5-nano` | Имя модели |
| `TELEGRAM_BOT_TOKEN` | нет | Токен бота |
| `TELEGRAM_CHAT_ID` | нет | Чат или канал, куда слать карточки |
| `LOG_LEVEL` | `INFO` | Уровень лога самого Watchdock |
| `BUFFER_SIZE_LINES` | `200` | Сколько последних строк держать на контейнер |
| `DEBOUNCE_WINDOW_SEC` | `5` | Сколько ждать соседние строки после первого срабатывания |
| `COOLDOWN_PERIOD_SEC` | `300` | Сколько молчать по той же сигнатуре после успешной отправки. Этот срок попадает в текст повтора |
| `MIN_SEVERITY` | `LOW` | Ниже этого уровня карточка не уходит. Значения: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` |
| `IGNORED_CONTAINERS` | пусто | Имена через запятую, помимо контейнера `watchdock` |
| `HOST_DISK_PATH` | `/` | Путь, у которого спрашивать свободное место |
| `HEARTBEAT_SEC` | `300` | Как часто писать в лог, что сайдкар жив, и обновлять файл heartbeat |
| `HEARTBEAT_PATH` | `/tmp/watchdock-heartbeat` | Файл, по которому HEALTHCHECK понимает, что цикл жив |
| `DOCKER_HOST` | в Compose `tcp://docker-proxy:2375` | Куда подключаться. В коде по умолчанию unix-сокет, Compose его подменяет |

Внутренние пределы в Compose не вынесены: строка не длиннее 2048 символов, буфер контейнера не больше 500 КБ, таймаут модели 10 секунд, в промпт не больше 80 строк и 24 000 символов, crash loop — больше 3 рестартов за 120 секунд и тишина 15 минут, Telegram пробует отправку 3 раза. `BUFFER_SIZE_LINES` и размер промпта сверху ограничены, чтобы переменная окружения не заказала гигабайтный буфер. Одновременно разбираются два инцидента.

## Если сайдкар молчит

Сокет или proxy недоступны. В логе будет пауза переподключения от 1 до 30 секунд. После сессии длиннее 30 секунд пауза снова начинается с одной. Список контейнеров и follow собираются заново. Пока пауза идёт, новых строк нет — это не пропавший кулдаун.

Модель не отвечает или ответила не по схеме. В чат уходит аварийная карточка, если Telegram принял её. Кулдаун после этого есть. Если не принял, следующая такая же ошибка снова дойдёт до отправки после debounce, а не через пять минут.

Telegram ответил 429. Пауза читает `Retry-After`, но не копится дольше 8 секунд. Если карточка так и не ушла, сигнатура не охлаждается.

Watchdock сам перезапустился. Кулдауны были только в памяти, они пустые. Хвост логов тоже пустой. Шторма по старым строкам не будет: подписка на логи идёт с `tail=0` и старое не перечитывает. Новая ошибка после рестарта снова станет карточкой.

В карточке «0 GB свободно», хотя на хосте место есть. Считается `HOST_DISK_PATH`. По умолчанию это корень контейнера, а не диск хоста. Примонтируйте нужный путь и укажите его.

Контейнер `watchdock` в статусе `Up`, а карточек нет и лог замер. HEALTHCHECK смотрит mtime `/tmp/watchdock-heartbeat`. Если файл старше двух `HEARTBEAT_SEC`, Docker перезапустит контейнер. Первые 600 секунд после старта проверка ещё не решает, жив ли процесс.

Пустой ключ или `MIN_SEVERITY=NOPE`. Процесс завершается в первую секунду и до proxy не доходит. В логе будет ошибка валидации настроек.

## Локальные тесты

Демон Docker для тестов не нужен. Сокет и `/proc` подменяются фикстурами.

```bash
cd watchdock
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/pip install --no-deps -e .
.venv/bin/pytest
.venv/bin/ruff check config.py main.py core schemas
.venv/bin/mypy config.py main.py core schemas
```

Образ ставит зависимости из `requirements.txt`, не с плавающих нижних границ. В GitHub Actions тот же набор: ruff, mypy, pytest и `docker build`. Демон в тестах по-прежнему не нужен.
